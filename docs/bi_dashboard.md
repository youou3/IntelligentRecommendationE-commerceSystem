# BI 看板设计说明

## 1. 文档目的

本文档用于说明前后端分离 BI 看板的设计方式，重点覆盖第一、二阶段测试辅助、运营观察和后续迭代复盘所需的核心指标、数据来源、接口和页面结构。

本看板定位为轻量级内部看板，不替代完整的数据仓库或专业 BI 平台，但应具备可视化、可筛选、可追踪、可扩展的能力。前端支持演示数据模式，即使没有本地数据库也能直接打开页面查看图表和交互。本次 UI 采用深蓝 + 蓝绿霓虹科技大屏风格，作为质量管控中心式控制台展示。

## 2. 看板目标

### 2.1 第一阶段辅助测试

看板需要帮助验证：

- 行为数据是否持续采集。
- 用户画像是否能正确生成。
- 推荐是否返回合理结果。
- 推荐曝光、点击、加购、转化是否能回流。
- 主要链路是否满足可追踪和可复盘要求。

### 2.2 第二阶段辅助测试

看板需要帮助验证：

- 余弦相似度推荐是否优于基础规则推荐。
- 业务过滤是否有效。
- 冷启动策略是否生效。
- 商品选品评分是否可区分爆品、潜力品、长尾品和风险品。
- 库存、毛利、曝光、点击、转化之间是否存在一致性。

### 2.3 后续运营复盘

看板需要支持：

- 运营问题定位。
- 商品和用户分层分析。
- 库存风险识别。
- 补货效果复盘。
- 推荐策略观察与迭代。

## 3. 总体架构

### 3.1 分层方式

看板采用前后端分离结构：

- 前端：`web/`，负责页面渲染、筛选、图表展示。
- 后端：Flask 提供 `/api/dashboard/*` 只读指标接口。
- 数据层：MySQL + MongoDB 作为数据来源。

### 3.2 关联关系

```text
前端 BI 页面
      |
      v
/api/dashboard/*
      |
      v
DashboardService
      |
      v
MySQL / MongoDB
```

### 3.3 设计原则

- 所有指标必须带 `tenant_id` 和 `merchant_id` 维度。
- 所有列表和趋势数据都应支持时间范围过滤。
- 推荐、选品、画像、库存四大模块应独立可视化。
- 图表数据应尽量直接返回前端所需结构，减少前端二次加工。

## 4. 数据来源

### 4.1 MySQL 来源

主要表：

- `products`
- `inventory`
- `user_profiles`
- `recommendation_feedback`
- `product_selection_snapshots`
- `orders`
- `order_items`

### 4.2 MongoDB 来源

主要集合：

- `behavior_events`
- `recommendation_logs`
- `inventory_warning_logs`
- `workflow_runs`
- `skill_call_logs`

### 4.3 指标口径说明

- 推荐请求数：来自 `recommendation_logs`。
- 曝光、点击、加购、转化：来自 `recommendation_feedback`。
- 行为事件趋势：来自 `behavior_events`。
- 用户画像分布：来自 `user_profiles`。
- 选品分层：来自 `products.product_layer` 和 `product_selection_snapshots`。
- 库存风险：来自 `inventory`。

## 6. 后端接口设计

### 6.1 总览接口

`GET /api/dashboard/overview`

用途：输出总体 KPI。

### 6.2 推荐漏斗接口

`GET /api/dashboard/recommendation-funnel`

用途：输出推荐漏斗和趋势。

### 6.3 商品选品接口

`GET /api/dashboard/product-selection`

用途：输出选品分层和商品风险。

### 6.4 用户画像接口

`GET /api/dashboard/user-profiles`

用途：输出用户画像分布。

### 6.5 库存健康接口

`GET /api/dashboard/inventory-health`

用途：输出库存健康状态。

### 6.6 补货复盘接口

`GET /api/dashboard/replenishment-review`

用途：输出补货单状态分布、建议量、审批量、入库率、采纳率、售罄率和补货商品后续销售表现。

### 6.7 运营复盘接口

`GET /api/dashboard/operations-review`

用途：聚合推荐效果、画像覆盖、选品风险、库存风险、补货复盘、MCP 调用健康和工作流运行情况，作为第五阶段运营复盘总入口。

### 6.8 通用参数

建议统一携带：

- `tenant_id`
- `merchant_id`
- `request_id`
- `start_date`
- `end_date`
- `scene`
- `category_id`
- `limit`

## 7. 前端页面设计

### 7.1 视觉风格

- 主色调：深蓝、青蓝、霓虹青绿、少量黄色高亮。
- 页面氛围：科技大屏、控制中心、仪表盘风格。
- 面板样式：发光边框、半透明卡片、细微扫描线效果。
- 数值样式：KPI 使用大字号和高对比亮色。
- 参考目标：类似质量管控中心大屏展示，不使用浅色普通后台风格。

### 7.2 交互按钮

- 刷新数据。
- 演示 / 真实模式切换。
- 重置筛选。
- 7 天 / 30 天快捷时间范围。
- 首页 / 详情页 / 购物车场景按钮。
- 健康商品 / 高转化 / 风险库存等快捷测试按钮。

### 7.3 页面结构

### 7.1 前端项目结构

前端放在 `web/` 目录，采用 Vue 3 + Vite + TypeScript + ECharts。

### 7.2 页面结构

首页单页布局：

- 顶部标题与筛选栏
- KPI 区
- 推荐漏斗区
- 商品选品区
- 用户画像区
- 库存健康区

### 7.3 交互方式

- 默认显示最近 7 天数据。
- 支持 tenant / merchant / scene / 时间范围筛选。
- 切换筛选条件后重新拉取所有看板接口。
- 各模块独立加载与错误展示。

## 8. 适配第一、二阶段测试的指标

### 8.1 第一阶段

重点看：

- 行为采集成功率
- 画像生成覆盖率
- 推荐曝光 / 点击 / 加购 / 转化
- 推荐漏斗转化率
- 行为和推荐日志是否能追踪到 request_id

### 8.2 第二阶段

重点看：

- 余弦相似度推荐结果
- 商品分层是否合理
- selection_score 分布
- 高分商品是否有足够库存
- 冷启动结果是否能够兜底

## 9. 可扩展方向

后续可在该看板基础上继续扩展：

- A/B 测试看板。
- 工作流运行看板。
- 补货效果复盘看板。
- 商家多租户对比看板。
- 报表导出与订阅能力。

## 10. 备注

当前 BI 看板属于轻量实现，主要用于辅助第一、二阶段测试和运营观察。后续若进入更成熟阶段，可将看板指标逐步沉淀为汇总表、快照表和更专业的分析层。

## 11. 第五阶段落地说明

第五阶段已在现有看板基础上补齐运营复盘能力：

- 后端新增 `GET /api/dashboard/replenishment-review`，用于补货效果复盘。
- 后端新增 `GET /api/dashboard/operations-review`，用于运营复盘总览。
- 前端补货页展示补货复盘 KPI、补货单列表、采纳率和售罄率。
- 前端工作流页展示运营复盘、MCP 调用健康和工作流健康。
- 所有新增接口继续按 `tenant_id + merchant_id` 过滤，避免跨商家数据泄漏。

### 11.1 运营复盘核心指标

- 推荐转化率。
- 用户画像覆盖率。
- 风险商品数量。
- 低库存商品数量。
- 补货单数量、建议量、审批率、入库率。
- SKILL 调用次数、失败次数、降级次数、平均耗时。
- WORKFLOW 运行次数和失败次数。

### 11.2 补货复盘口径

- `approval_rate`：进入审批通过、采购、在途、已入库、已关闭状态的补货单数 / 补货单总数。
- `receive_rate`：已入库或已关闭补货单数 / 补货单总数。
- `fulfill_rate`：审批量 / 建议补货量。
- `sell_through_rate`：周期内支付销量 / 审批量或建议补货量。
