# 系统架构说明

## 1. 文档目的

本文档用于统一系统的分层方式、模块边界和职责划分，重点说明 Flask API、MCP、SKILL、WORKFLOW 与数据层的关系。相关接口、数据库和工作流细节分别见 [api.md](api.md)、[database.md](database.md) 和 [workflow_design.md](workflow_design.md)。

## 2. 总体分层

### 2.1 Flask API 层

职责：

- 接收请求。
- 完成鉴权、参数校验、租户识别。
- 做接口路由和基础响应封装。
- 不承载复杂业务规则。

### 2.2 MCP 调度层

职责：

- 统一注册和发现 SKILL。
- 根据场景选择对应能力。
- 统一管理调用日志、耗时和异常。
- 向 WORKFLOW 提供标准调用入口。

### 2.3 SKILL 能力层

职责：

- 封装单一业务能力。
- 处理画像、推荐、选品、库存预警、补货建议等独立逻辑。
- 只处理本职能力，不混入流程编排。

### 2.4 WORKFLOW 流程层

职责：

- 编排跨模块流程。
- 处理库存预警、自动补货、审批流等跨能力协作。
- 不直接实现复杂算法。

### 2.5 数据层

职责：

- MySQL 保存结构化业务数据。
- MongoDB 保存行为事件、曝光日志、反馈日志等事件数据。
- Redis 保存热点画像、推荐结果、库存风险等缓存数据。

## 3. 核心边界原则

- API 层只做请求接入，不做重业务计算。
- MCP 只做能力调度，不直接写业务规则。
- SKILL 只做单点能力，不互相依赖。
- WORKFLOW 只编排，不嵌入复杂业务算法。
- 数据库只保存状态和事件，不承担流程逻辑。

## 4. 多租户架构约束

### 4.1 租户边界

- 所有核心对象都应支持 `tenant_id` 过滤。
- 所有查询默认按租户边界执行。
- 所有聚合统计默认按租户维度分组。

### 4.2 请求链路

建议请求链路包含：

- `tenant_id`
- `merchant_id`
- `request_id`
- `scene`
- `event_id`

### 4.3 数据隔离

- 行为数据、推荐结果、库存数据、补货记录都应按租户隔离。
- 商家后台只能看到本租户数据。
- 工作流运行记录必须可追踪到租户。

## 5. 推荐的模块关系

### 5.1 推荐链路

Flask API -> MCP -> 用户画像 SKILL / 推荐 SKILL -> 数据层

### 5.2 库存链路

Flask API 或定时任务 -> WORKFLOW -> 库存预警 SKILL / 补货建议 SKILL -> 数据层

### 5.3 行为链路

前端埋点 -> Flask API -> MongoDB 事件集合 -> 画像更新任务 -> MySQL 画像表
