# 中小型智能电商 SaaS 系统架构、接口与多租户预留说明

## 1. 文档目的

本文档用于补充迭代开发文档中未展开的基础约束，重点说明：

- 多租户预留字段。
- 核心架构边界。
- 接口命名与通用约束。
- 数据库与事件模型的预留要求。

本文档不替代迭代规划，而是作为后续开发、建表和接口实现的统一约束。主规划见 [开发文档_迭代功能.md](开发文档_迭代功能.md)，索引见 [docs/README.md](README.md)。

## 2. 多租户预留字段

### 2.1 设计原则

系统从第一版开始就按 SaaS 多租户场景设计，所有核心对象都必须默认考虑租户隔离，避免后续补字段时出现历史数据迁移、权限判断遗漏或跨租户泄漏问题。

### 2.2 推荐预留字段

所有核心业务表、核心接口入参、核心日志记录建议统一预留以下字段：

- `tenant_id`：租户 ID，核心隔离字段。
- `merchant_id`：商家 ID，标识具体商家主体。
- `org_id`：组织或门店 ID，适用于连锁门店场景。
- `project_id`：项目空间 ID，适用于一个租户下多业务线场景。
- `scene`：业务场景，例如首页、详情页、购物车页。
- `request_id`：请求链路追踪 ID。
- `event_id`：事件幂等 ID。
- `operator_id`：操作人 ID，适用于人工审批、运营配置、后台管理等场景。

### 2.3 必须支持租户隔离的对象

以下对象必须在设计阶段就支持按租户过滤：

- 用户表。
- 商品表。
- 订单表。
- 用户画像表。
- 库存表。
- 补货单表。
- 行为事件表或集合。
- 推荐曝光表或集合。
- 库存预警记录表或集合。
- 审批记录表。

### 2.4 查询与写入约束

- 所有查询默认必须带租户条件。
- 所有写入必须带租户上下文。
- 推荐、画像、库存、补货等链路数据必须可按租户独立统计。
- 不允许出现跨租户聚合后再做业务判断的默认实现。
- 接口分页、排序、筛选均应在租户边界内执行。

## 3. 架构边界说明

### 3.1 分层职责

#### Flask API 层

职责：

- 接收请求。
- 完成鉴权、参数校验、租户识别。
- 做接口路由和基础响应封装。
- 不承载复杂业务规则。

#### MCP 调度层

职责：

- 统一注册和发现 SKILL。
- 根据场景选择对应能力。
- 统一管理调用日志、耗时和异常。
- 向 WORKFLOW 提供标准调用入口。

#### SKILL 能力层

职责：

- 封装单一业务能力。
- 处理画像、推荐、选品、库存预警、补货建议等独立逻辑。
- 只处理本职能力，不混入流程编排。

#### WORKFLOW 流程层

职责：

- 编排跨模块流程。
- 处理库存预警、自动补货、审批流等跨能力协作。
- 不直接实现复杂算法。

#### 数据层

职责：

- MySQL 保存结构化业务数据。
- MongoDB 保存行为事件、曝光日志、反馈日志等事件数据。
- Redis 保存热点画像、推荐结果、库存风险等缓存数据。

### 3.2 核心边界原则

- API 层只做请求接入，不做重业务计算。
- MCP 只做能力调度，不直接写业务规则。
- SKILL 只做单点能力，不互相依赖。
- WORKFLOW 只编排，不嵌入复杂业务算法。
- 数据库只保存状态和事件，不承担流程逻辑。

## 4. 接口统一约束

### 4.1 通用入参字段

建议所有接口按场景统一携带以下字段：

- `tenant_id`
- `merchant_id`
- `request_id`
- `scene`
- `user_id`
- `product_id`
- `event_id`

### 4.2 通用返回结构

建议统一返回格式：

```json
{
  "success": true,
  "code": "OK",
  "message": "success",
  "request_id": "REQ10001",
  "data": {}
}
```

### 4.3 接口设计要求

- 所有写接口必须具备幂等能力，至少支持 `event_id` 或业务唯一键。
- 所有上报接口必须支持追踪 ID。
- 所有列表接口必须支持分页。
- 所有查询接口必须默认按租户隔离。
- 所有推荐类接口必须支持场景参数。
- 所有库存和补货接口必须返回状态机字段，方便前端展示流转过程。

### 4.4 接口文档建议补齐项

每个接口文档建议补齐以下内容：

- 接口名称。
- 请求方法。
- 路径。
- 鉴权方式。
- 请求参数。
- 响应参数。
- 错误码。
- 幂等规则。
- 限流规则。
- 日志字段。
- 示例请求与响应。

## 5. 数据库与事件模型约束

### 5.1 MySQL 结构化表建议

建议至少包含以下表，并为每张表预留租户字段：

- `users`
- `products`
- `orders`
- `order_items`
- `user_profiles`
- `inventory`
- `inventory_logs`
- `replenishment_orders`
- `approval_records`
- `recommendation_feedback`

### 5.2 MongoDB 事件集合建议

建议至少包含以下集合：

- `behavior_events`
- `recommendation_logs`
- `inventory_warning_logs`
- `workflow_runs`
- `skill_call_logs`

### 5.3 事件模型要求

每个事件至少应包含：

- `tenant_id`
- `merchant_id`
- `event_id`
- `request_id`
- `event_type`
- `scene`
- `created_at`

行为和反馈类事件建议额外包含：

- `user_id`
- `product_id`
- `category_id`
- `source`
- `payload`

### 5.4 状态类数据要求

对于库存、补货单、审批单等状态类对象，建议统一具备：

- 当前状态。
- 状态更新时间。
- 状态流转记录。
- 操作人信息。
- 关联事件 ID。
