# 工作流设计说明

## 1. 文档目的

本文档用于统一库存预警、自动补货等流程型能力的设计方式，重点说明工作流触发、状态流转、输入输出和可追踪性要求。相关能力定义见 [mcp_skill_design.md](mcp_skill_design.md)、[api.md](api.md) 和 [database.md](database.md)。

## 2. 工作流设计原则

- 工作流只负责流程编排，不承载复杂算法。
- 工作流中的每个节点应尽量只做一件事。
- 工作流必须可追踪、可重试、可回放。
- 所有工作流运行记录必须带租户维度。
- 工作流状态应能落库，方便前端和后台查询。

## 3. 核心工作流

### 3.1 库存预警工作流

#### 触发方式

- 定时触发：每小时检查一次库存。
- 事件触发：订单支付成功后检查相关商品库存。
- 事件触发：退款、取消订单、入库完成后重新计算库存状态。

#### 流程节点

1. 读取库存数据。
2. 读取近 7 天销量数据。
3. 调用库存预警 SKILL。
4. 判断预警等级。
5. 写入预警记录。
6. 推送预警到商家后台。
7. 如有需要，触发自动补货工作流。

#### 输出结果

- 预警等级。
- 预警原因。
- 预警商品列表。
- 后续处理建议。

### 3.2 自动补货工作流

#### 触发方式

- 库存预警触发。
- 商家手动触发。
- 爆品识别后自动触发。

#### 流程节点

1. 获取预警商品。
2. 调用智能选品 SKILL 获取商品价值分。
3. 调用补货建议 SKILL 计算建议补货量。
4. 生成补货单。
5. 商家审批。
6. 审批通过后生成采购单或补货单。
7. 入库后更新库存。
8. 写入实际销售表现，用于模型修正。

#### 输出结果

- 建议补货量。
- 审批状态。
- 补货单状态。
- 入库结果。

## 4. 状态机约束

### 4.1 库存预警状态

建议状态：

- `pending`
- `triggered`
- `notified`
- `resolved`
- `closed`

### 4.2 补货单状态

建议状态：

- `draft`
- `pending_approval`
- `approved`
- `rejected`
- `purchasing`
- `in_transit`
- `received`
- `closed`

### 4.3 审批状态

建议状态：

- `pending`
- `approved`
- `rejected`
- `cancelled`

## 5. 运行记录要求

每次工作流执行都应记录：

- `tenant_id`
- `merchant_id`
- `workflow_name`
- `run_id`
- `request_id`
- `status`
- `input_payload`
- `output_payload`
- `error_message`
- `started_at`
- `finished_at`

## 6. 异常与重试

- 可重试节点应具备幂等能力。
- 关键节点失败后应允许按 run_id 或 request_id 重放。
- 工作流超时应写入失败原因，避免静默失败。
- 工作流重试不能重复生成业务单据。

## 7. 接口与工作流关系

- 接口只负责发起请求和查询状态。
- 工作流负责异步流程推进。
- 接口返回时应给出 `request_id` 或 `run_id`，便于追踪。
- 前端查询应以运行记录和状态表为准。

## 8. 备注

后续若工作流复杂度提升，可以继续拆出：

- 审批流设计。
- 补货策略设计。
- 库存状态机设计。
